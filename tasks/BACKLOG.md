# BACKLOG — Emiva

רישום של "לא היום" — פריטים שהושהו בכוונה. כל פריט חייב **trigger**
(מה יגרום לנו לחזור אליו) ו-**owner**. בלי trigger — לא נכנס כאן.

## איך להשתמש

- לפני סגירת כל טאסק: אם נאמר "לא היום / בטאסק נפרד / להרחיב אחר כך" →
  חייב להיכנס לכאן.
- לפני פתיחת כל טאסק חדש: 2 דקות סקירה של הרשימה. אם trigger נדלק — הוא
  קופץ ראשון בתור.
- כשאפשר: להפוך פריט ל-**eval שנכשל** תחת `evals/backlog/` במקום
  להישאר כאן. eval שנכשל = הזיכרון עבר ל-CI.
- שיטות trigger ב-Emiva (מ-CLAUDE.md §Backlog triggers):
  - **מדידה אובייקטיבית** — `telemetry` (sessions, repetition rate, mastery).
  - **משוב אנושי** — הערה ב-[FEEDBACK-LOG.md](FEEDBACK-LOG.md).
  - **eval נכשל** — אוטומטי ב-CI / `npm run eval:backlog`.
  - **קצב סקירה קבוע** — כל יום ראשון, 2 דקות.

#### שחזור מבוקר (2026-08-10) — האבחנה המקורית הייתה שגויה

הועלה שרת פיתוח ונוספו 5 קבצים בבת אחת כדי לשחזר. הממצאים:

| הנחה קודמת | מה שנמצא בפועל |
|---|---|
| "מטמון webpack נשבר" | **Turbopack נופל באותה שגיאה בדיוק** — לא באג של webpack |
| "צריך לנקות את `.next`" | הפעלה מחדש **בלי לנקות** (136MB נשארו) תיקנה הכל |
| "הקבצים החדשים מקלקלים" | השרת **לא מתאושש** גם אחרי שהוסרו |

**המסקנה:** הבעיה היא **מצב בזיכרון של התהליך החי**, לא קבצים
שנפגמו על הדיסק. מחיקת `.next` "עבדה" רק כתופעת-לוואי — היא
כפתה הפעלה מחדש. לכן המעבר ל-Turbopack, שהיה הפתרון המתוכנן,
**לא היה פותר כלום.**

**ממצא נלווה:** נמצאו 4 תהליכי שרת-פיתוח חיים בו-זמנית, אחד מהם
יתום מסשן קודם. שרתים יתומים מחזיקים פורטים ומצב ישן, וסביר שהם
חלק מהתקלה. `dev:restart` סוגר את כולם.

**הסתייגות ביושר:** בשחזור השני אותו רצף **לא** הפיל את השרת.
התקלה **לא דטרמיניסטית**, ולכן אי אפשר להצהיר "נפתר" — רק
"יש כלי מהיר שמחזיר לתקין, והאבחנה שהובילה לפתרון-שגוי תוקנה".

#### ממצא נוסף: זה פוגע גם ב-`npm run build`, לא רק בשרת הפיתוח

במהלך הוולידציה `npm run build` נכשל שלוש פעמים ברצף — **וכל פעם
על עמוד אחר**: `/journal/puppy`, `/404`, `/parent/history`. השגיאה
תמיד מאותה משפחה (`Cannot find module for page`).

נבדק שזה **לא** נגרם מהשינויים שלי: הכנסתי את העבודה ל-stash,
בניתי על HEAD נקי לגמרי — **ונכשל גם שם**. אחר כך, בלי שינוי קוד,
שלוש בניות רצופות **עברו** (3/3).

**המשתנה שהבדיל:** בכשלונות רצו במקביל שרתי-פיתוח שנגעו
ב-`.next`; בהצלחות לא. כלומר **`.next` משותף בין שרת חי לבין
build הוא מירוץ-כתיבה** — שני תהליכים כותבים לאותה תיקייה.

**מסקנה מעשית:** לא מריצים `npm run build` בזמן ששרת פיתוח חי.
`npm run dev:restart` סוגר את כולם, ולכן הוא גם ההכנה הנכונה
לבנייה. זה גם מסביר את "השבירות בלי שינוי מבני מקדים" מ-2026-04-23.

- **מה נעשה (2026-08-10):** `npm run dev:restart` — סוגר כל שרת-פיתוח
  חי (כולל יתומים) ומעלה מחדש בלי לגעת במטמון. אומת: זיהה 4 שרתים,
  עלה תוך 2.7 שניות, `/session` חזר 200, ו-VS Code + Claude לא נפגעו.
  `dev:clean` נשאר כגיבוי למקרה של מטמון שבאמת נפגם.
- **סטטוס:** 🟡 מוקל, לא סגור. נשאר פתוח עד שיעברו **שבועיים בלי
  אף שבירה**, או עד שתופיע שבירה ש-`dev:restart` לא מתקן — אז
  צריך חקירה עמוקה יותר (למשל antivirus שנועל קבצים בזמן כתיבה).
- **Why it matters now:** כשהבנות יושבות והאפליקציה נופלת, הן
  לא מתרגלות. זה הפך מרעש-פיתוח לחסם-שימוש.
